# OnReady Notification Overview (Phase 0)

Planning notes aligning `go-notifications` OnReady work with `go-export` and admin integration.

## Inputs Reviewed
- `NOTIF_TDD.md` (go-notifications export integration goals and fields).
- `docs/prds/EXPORT_TDD.md` (go-export pipelines, delivery hooks, manifest/multipart expectations).
- `go-admin-architecture-updated.md` (module boundaries and adapter-first stance).

## Ownership & Boundaries
- **Definition/Template**: go-notifications owns the reusable `export.ready` definition and email/in-app templates (placeholders: `file_name`, `format`, `url`, `expires_at`, optional `rows`, `parts`, `manifest_url`, `message`); no dependency on go-export.
- **Registration Helper**: go-notifications ships idempotent installer (namespaced option) that can be invoked by hosts or go-export adapters; helper returns definition code/IDs for DI wiring.
- **Sender Interface**: go-notifications owns `OnReadyNotifier` + `OnReadyEvent` and wraps the existing manager/commands; go-export (or any module) calls it without importing internal packages.
- **Channel Metadata**: go-notifications maintains per-channel metadata defaults (email subject/body/CTA, in-app title/body/icon/badge) and localization keys; go-export provides values/overrides at send time.
- **Manifest/Multipart**: go-notifications templates surface optional `ManifestURL` + `Parts`; go-export is responsible for producing manifest links/multipart counts when applicable.
- **Triggers & Preferences**: go-export (jobs/UI) triggers sends; go-notifications enforces preferences/rules and routing. Activity/audit events remain in go-export per `EXPORT_TDD` (verbs `export.requested/completed/failed`).

## Alignment Notes
- Delivery hook in `EXPORT_TDD` maps to `OnReadyNotifier.Send` with the same payload fields; keep interface minimal to avoid go-export dependency on internal notifier packages.
- Default definition code should be `export.ready` with optional namespace prefix to avoid collisions when multiple exporters register in one host.
- Prefer email + in-app variants only (per TDD scope); SMS/push remain out of scope unless added by host adapters.
- Localization keys live in go-notifications; go-export should pass raw values and let template/i18n resolve localized strings.
- Manifest handling: when `Parts` > 1 or `ManifestURL` present, templates must surface both the primary file URL and manifest CTA; otherwise, render a single export link.

## Next Steps for Implementation
- Land the assets/helpers in go-notifications (Phase 1–3 of `NOTIF_TSK.md`), then expose a small adapter in go-export that calls the registration helper and `OnReadyNotifier`.
- Coordinate with go-admin UI blocks (export history/forms) to ensure any manifest URLs generated by go-export are forwarded into the notifier payload.
- Add release/migration notes clarifying opt-in nature and default definition code.
